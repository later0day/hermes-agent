1. 一句话定位

Agent Room 是什么
一个 DingTalk 群 ↔ 一份 成员 profile 名册 + 一个自动生成的 观察者 profile。 群里的消息由观察者判断该路由到哪个成员 profile 应答，成员回复异步发回原群。

本文档覆盖 Agent Room 完整四期规划（M1 → M4）：
  • M1（本次开发目标）：手动创建 room、手动绑定群、单成员路由、异步回复 —— 拿到详细技术规格 + 前置架构 spike + 完整验收方案
  • M2 / M3 / M4：自动规划、并发多成员、任务拆分 —— 拿到范围边界、工作量粗估、依赖关系、验收标准 + 线上测试方案
详见 §2 路线图和 §11 各期验收。

与 hermes-agent 现有概念的关系

现有概念Agent Room 如何用
Profile 观察者和成员都是普通 profile 目录（~/.hermes/profiles/<name>/），完全同构。观察者只是自动生成 + 打了 .observer 标记文件。
SourceAgentBinding 复用现有绑定表，通过 fallback_extra.room_id JSON 字段扩展，零迁移、完全向后兼容。旧的"群→单 profile"绑定继续正常工作。
_profile_runtime_scope 核心原语——临时切换 HERMES_HOME + secret scope。Room 路由的"先跑观察者、再跑成员"两次 turn 直接嵌套/串接它。
Kanban decompose M1 借鉴其 aux LLM 分诊模式的设计，但独立实现（输入是群消息，输出是 tool call）。M4 才复用其任务图能力。
request_hard_interrupt + get_active_subagent_parent 观察者 route_to_member 工具执行后强制中断 agent loop，避免继续 iterate 浪费 token。

① 系统全景 · Room 在 hermes-agent 中的位置

从 IM 平台入站消息到 agent 应答的完整数据流，Room 层是叠加在现有单 profile 通路上的新分支

关键点：Room 分支是叠加在现有单 profile 通路上的第二种绑定形态，通过 SourceAgentBinding.fallback_extra.room_id 区分。所有现有的"群→单 profile"绑定继续走绿色分支，零迁移。

② 数据模型 · 三个存储位置的关系

Room 数据分散在三处：新表 agent_rooms、扩展现有 SourceAgentBinding、profile 目录

一致性维护：三处存储的 CRUD 需要保证同步。创建 room：先建 profile 目录 → 再插 rooms 表；删除 room：先解绑（清 fallback_extra.room_id）→ Fence → 删 rooms 表 → 删 profile 目录。M1 需要一个孤立数据扫描修复逻辑跑在 gateway 启动时。

③ 消息路由时序 · 5 步 + 摘要注入

从群消息到达到成员回复的完整时序，含 N4 轻量分类分支和 §8 跨成员摘要注入

关键防抖：STEP 2 的轻量分类（N4）是核心成本控制——话题延续时直接沿用上次路由，避免每条消息都跑完整 observer turn。关键 loop 终止：STEP 3b 里的 request_hard_interrupt 是 M1 唯一必做的架构补丁，避免观察者调完 tool 后继续 iterate 浪费 token。

④ 观察者 Profile 内部结构

观察者是普通 profile 目录，通过 4 个特殊约定被锁定成"只能路由不能干活"

⑤ Session ID 三层命名空间

Room 用两种确定性 session_id 隔离观察者与成员，不影响现有单聊 session_key

⑥ Fence 机制 · 保护正在跑的 turn 不污染新状态

当 room 结构发生变动时，正在执行的 agent turn 输出被丢弃，防止旧状态迟到污染

为什么需要 Fence：如果不做这个保护，用户 unbind 后正在跑的 observer 完成 → 派发成员 → 成员完成 → session_webhook 发消息回群——群已经解绑但收到了一条迟到的 room 消息，用户会困惑。M1 简化版 Fence 只在 room 结构变化 时触发（Studio 版本是每消息细粒度 fence），对 M1 场景足够。

4. M1 数据模型

4.1 新表 agent_rooms

存储位置：~/.hermes/gateway_agent_rooms.sqlite，与 gateway_source_agent_bindings.sqlite 同级。运行时数据，不入 profile 目录。

CREATE TABLE agent_rooms (
    room_id           TEXT PRIMARY KEY,        -- 形如 "room_ab12cd34"
    room_name         TEXT NOT NULL UNIQUE,    -- 用户可读名，形如 "客户支持组"
    description       TEXT NOT NULL DEFAULT '',
    observer_profile  TEXT NOT NULL,           -- 观察者 profile 名
    members_json      TEXT NOT NULL DEFAULT '[]',  -- ["客服","财务","技术"]
    default_member    TEXT NOT NULL DEFAULT '',    -- 兜底路由目标
    created_at        INTEGER NOT NULL,
    created_by        TEXT NOT NULL DEFAULT '',
    updated_at        INTEGER NOT NULL,
    updated_by        TEXT NOT NULL DEFAULT ''
);

CREATE UNIQUE INDEX idx_agent_rooms_name ON agent_rooms(room_name);
为什么不建 room_members 独立表
成员就是 profile 名的字符串数组，profile 是文件系统目录不是 SQL 表，建外键关联意义不大。 M1 用 members_json 存字符串数组，配合 N3 硬上限 5 个 完全够用。 M3 阶段需要给成员挂更多元数据时再迁移到独立表。

5.2 SOUL.md 模板

# Observer Agent for Room: {room_name}

You are the observer for a group of specialized agents. Your job is to read
incoming messages and decide which member should respond.

## Room description
{room.description}

## Members
- **{member_1}**: {member_1.description}
- **{member_2}**: {member_2.description}
- **{member_3}**: {member_3.description}

## Your workflow
1. Read the latest message (see conversation history).
2. Determine whether this is a NEW topic or a continuation.
   - Continuation: keep routing to the same member as last time.
   - New topic: pick the best-matching member by their descriptions.
3. Emit your routing decision by calling `route_to_member` with:

   - `reason`: 1-sentence explanation (see §8 for cross-member summary rules)

Do NOT write any user-facing reply yourself.
Your only output is the `route_to_member` tool call.

5.3 route_to_member 工具 + Loop 终止（M1 关键实现）

tools/room_router_tool.py

def route_to_member(
    member: str,
    reason: str,
    is_new_topic: bool = False,
) -> dict:
    """Emit a routing decision. Called by the observer agent only."""

    # 拿到当前正在跑的 agent 实例（ContextVar 已经在 tool 调度期间绑定）
    from agent.subagent_lifecycle import get_active_subagent_parent
    from agent.interrupt_compat import request_hard_interrupt

    agent = get_active_subagent_parent()
    if agent is not None:
        # 强制中断 agent loop，避免继续 iterate 浪费 token
        request_hard_interrupt(agent, f"Route decided: {member}")

    return {
        "action": "route_to_member",
        "member": member,
        "reason": reason,
        "is_new_topic": is_new_topic,
    }
Spike 结论：终止机制零件全在
agent/subagent_lifecycle.py::get_active_subagent_parent 已经通过 _ACTIVE_PARENT_AGENT ContextVar 在 tool 调度期间绑定当前 agent； agent/interrupt_compat.py::request_hard_interrupt 是现成的强制中断。 不需要改 agent runtime、不需要新的 turn 终止协议。

5.4 N4 · 轻量分类先行

观察者跑完整 agent turn 有成本。M1 用一个 aux LLM 前置过滤：

消息进入 ↓ 【轻量分类 aux LLM】(复用 agent/auxiliary_client.py) ├── 输入: 最近5条历史 + last_routed_member（内存缓存） └── 输出: { is_new_topic: bool, confidence: float } ↓ if is_new_topic == False && confidence > 0.7 && last_routed_member 存在: → 沿用 last_routed_member，跳过观察者 turn else: → 触发完整观察者 turn
last_routed_member 只在内存里缓存（不落库），进程重启后失效。重启后第一条消息触发完整观察者判断，这是正常代价——避免额外 IO，且 Fence 时天然失效。

6. 运行时路由完整流程

入口分支（gateway/run.py）

def _resolve_room_for_source(self, source) -> Optional[RoomBinding]:
    binding = self._source_agent_binding_store.get_binding(
        build_source_binding_key(source)
    )
    if not binding:
        return None
    room_id = (binding.fallback_extra or {}).get("room_id")
    if not room_id:
        return None
    return self._agent_room_store.get_room(room_id)

# 在 process_message 主分支前置：
room = self._resolve_room_for_source(source)
if room:
    return await self._process_message_via_room(message, source, room)
# 否则走现有单 profile 流程（不变）

6.1 异步路由五步（含 §8 摘要注入）

1 立刻回一句 "已收到，正在为你选择处理人..." └─ 通过 DingTalk session_webhook，不进入任何 agent turn 2 轻量分类 aux LLM 调用（§5.4） └─ 输出 { is_new_topic, confidence } 3 路由决策 ├─ 沿用: target_member = last_routed_member └─ 或跑完整观察者 turn: ├─ 加载 observer_profile 的 HERMES_HOME ├─ 使用 _profile_runtime_scope（ContextVar 隔离，async-safe） ├─ session_id = room_observer:{room_id} ├─ 观察者输出 route_to_member 工具调用 ├─ 提取 target_member, reason, is_new_topic ├─ 校验 target_member ∈ members_json，否则用 default_member └─ 更新 last_routed_member 内存缓存 4 更新群消息 "转交给 {target_member} 处理..." └─ 用 DingTalk adapter 的 edit_message（fork 已实现） 4.5 跨成员摘要注入（§8） └─ 如果 reason 字段含跨成员摘要，拼到给成员的消息前面作为 context prefix 5 派发成员执行 ├─ 加载 target_member profile 的 HERMES_HOME ├─ session_id = room_member:{room_id}:{target_member} ├─ 走 hermes-agent 现有 _run_agent_inner 完整 turn └─ 成员输出通过 session_webhook 发回原群

6.2 Session ID 命名约定

用途命名生命周期
观察者 session room_observer:{room_id} Room 生命周期内持续；上下文小（只调工具不产文本）
成员 session room_member:{room_id}:{member_profile} Room 生命周期内持续；跟单聊 session 完全隔离
非 room 单 profile 绑定 不变，走 build_session_key 不变

6.3 Session Fence（借鉴 Studio）

AgentRoomStore 内存维护 fenced_sessions: set[str]。触发 Fence 的操作：

  • 删除 room
  • 解绑群
  • 成员名册变动

触发时把当前 room 所有活跃 session（观察者 + 成员）加入 Fence 集合。每次回消息前检查 session 是否被 fenced——是则丢弃输出，防止"清空后旧 turn 迟到污染新状态"。

M1 只在 room 结构变化时 Fence，不做 Studio 那种每消息细粒度 Fence。此简化对 M1 场景够用。

8. 跨成员上下文摘要（M1 关键补丁）

M1 简化取舍的 UX 断崖
M1 里成员的 session 只包含"自己被路由过的历史"，看不到"另一个成员之前说了什么"。 真实场景例：用户先问客服"怎么退款"→客服答→用户接着问"再问下之前的账单"→观察者 判断话题延续但换到财务→财务 profile 看不到之前客服的对话，只看到"再问下之前的账单"。

缓解方案 · 在 M1 里必须做

  1. 观察者 SOUL.md 加规则：当检测到 is_new_topic=False 且要换成员时，在 reason 字段带上"上一位成员最后回复的一句摘要"
  2. Room router 在派发前解析 reason：如果含跨成员摘要，前置到给成员的消息

格式约定

> 上一位处理人 {previous_member} 的回复摘要：{summary}
> ---
> 用户消息：{original_message}
这不是 M3 那种完整 context-projection（Studio 的单人称改写），只是最小可用的缓解。 M3 会完整替换掉这一层。但 M1 交付时必须至少有这个，否则用户第一次跨成员对话就会觉得系统很傻。

  • 复杂任务拆分：给一个明显需要多步的需求（"帮我起草合同 + 找财务算成本 + 发给客户"），观察者调 decompose_and_route → 3 个子任务按依赖顺序执行
  • 依赖失败传播：中间某个子任务失败 → 后续依赖它的子任务不执行 → 观察者综合 turn 里能看到失败信息
  • 回归 M1：普通对话依然走 M1 单成员路径

线上真实环境测试

测试步骤

  1. 在群里发简单问题 → 应走 M1/M3 单成员路径（可看日志确认 route_to_member 而非 decompose_and_route）
  2. 发复杂问题："帮我起草这份合同，然后让财务估算成本，最后综合给客户一个方案" → 应走 decompose_and_route → 拆成 3 个子任务
  3. 验证子任务在 kanban 里可见，assignee 正确 = room 成员
  4. 依赖顺序：合同起草完成前，客户方案子任务不启动
  5. 全部完成后 → 观察者综合 turn 生成最终回复发到群
  6. 中间人为让某个子任务失败 → 后续依赖子任务不执行 → 综合 turn 里带上失败信息

测试通过判定

  • 观察者能自主判断"简单 vs 复杂"，且判断合理（简单问题不拆分）
  • 子任务在 kanban 里可查、可追踪
  • 综合 turn 的最终回复包含所有子任务的关键信息
  • M1/M2/M3 的验收 case 全过

跨期回归测试原则

每期交付前都必须回归运行前期的所有验收 case。M4 交付时要跑 M1+M2+M3 全部 case；M3 交付时跑 M1+M2 全部 case。用 scripts/run_tests.sh 的 per-file 隔离模式跑（避免模块状态泄漏）。
